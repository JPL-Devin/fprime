# F´ Unit Test Author skill (canonical)

You write or expand unit tests for F Prime components using **gtest** plus the
F Prime test harness (`STest`). Tests are produced under each component's
`test/ut/` directory and are run via `fprime-util check`.

This skill is the canonical, tool-independent version. It is referenced by the
repo-root [`AGENTS.md`](../AGENTS.md) and by tool-specific wrappers.

## When to use

- The user asks for new tests for a component (or a new component just
  authored via [`component-author.md`](component-author.md)).
- The user asks to expand existing coverage (new commands, new ports, edge
  cases, off-nominal paths).
- The user asks to add regression tests for a specific bug fix.

## What to produce

Per component, the typical layout is:

```
<Component>/
├── <Component>.fpp
├── <Component>.cpp
├── <Component>.hpp
└── test/
    └── ut/
        ├── Tester.hpp
        ├── Tester.cpp
        ├── TesterBase.hpp / TesterBase.cpp        (autogenerated)
        ├── GTestBase.hpp  / GTestBase.cpp         (autogenerated)
        └── main.cpp                               (or per-test files)
```

You produce:

1. A `Tester` class derived from the autogenerated `<Component>GTestBase` that
   exposes test scaffolding (port connections, invocation helpers, history
   accessors).
2. Per-behavior test cases that:
   - Invoke handlers via the `Tester` helpers (not by reaching into the
     component directly).
   - Assert on the resulting events, telemetry, commands, and port outputs by
     inspecting the gtest-friendly histories provided by the base class
     (`ASSERT_EVENTS_*`, `ASSERT_TLM_*`, `ASSERT_CMD_RESPONSE_*`, etc.).
   - Cover nominal paths, every off-nominal path, and the edges (empty,
     boundary sizes, invalid opcodes, malformed serialized data, repeat
     calls, shutdown ordering, etc.).
3. A test entry point (existing `main.cpp` if present, otherwise add one)
   that calls `::testing::InitGoogleTest` and `RUN_ALL_TESTS`.

## Procedure

1. Read the component's FPP model first. Every port, command, event,
   telemetry channel, and parameter is a test-target.
2. Look at the autogenerated `<Component>GTestBase.hpp` / `TesterBase.hpp` to
   discover the assertion helpers and history APIs you will use. Never
   hand-edit those autogenerated files.
3. Pattern-match against existing tests in neighboring components for
   style — for instance `Svc/CmdSequencer/test/ut`, `Svc/DpCatalog/test/ut`,
   or `Drv/Ip*/test/ut`. F´ has strong conventions; do not invent a new test
   shape.
4. Tests must be **deterministic** and self-contained. Do not depend on real
   filesystems, networks, time, or threading except through `STest` helpers
   that simulate them.
5. For active components, use `STest::Random` for randomized inputs and seed
   it from a fixed value so failures reproduce.
6. Cover **every** event your changes can emit, including the off-nominal
   ones. A missing assertion is a coverage gap, not a stylistic preference.
7. Run `fprime-util generate` (if any FPP changed), then `fprime-util build`,
   then `fprime-util check`. Iterate until all tests pass.
8. Run `fprime-util format` (or rely on the pre-commit hook) before
   committing.

## Constraints (from [`code-review.md`](code-review.md))

- Test code must compile under C++14. No exceptions, RTTI, `std::string` in
  production code under test; test code may use gtest's `EXPECT_*`/`ASSERT_*`
  macros and `std::string` *within tests only*, consistent with existing F´
  unit tests.
- `friend` declarations on production classes are acceptable **only** to let
  test code reach internals.
- Do not introduce dynamic allocation in the component under test through the
  test harness.
- Do not edit autogenerated files (`*ComponentAc.*`, `*TesterBase.*`,
  `*GTestBase.*`). Re-run `fprime-util generate` and `fprime-util impl` if
  scaffolding looks stale.
- New tests **must** run in CI via `fprime-util check`. Tests that are
  marked `DISABLED_` should be rare and justified in a comment.
- Bug-fix PRs **must** add a regression test that fails on the un-fixed code
  and passes on the fixed code.

## Output Format

When working interactively, produce changes in this order:

1. Any FPP/autocoder regeneration commands the user should run (only if the
   FPP changed).
2. The `Tester` and test source files, one at a time.
3. The shell commands to build and run the new tests (`fprime-util build` and
   `fprime-util check`).
4. A coverage summary: which ports/commands/events/channels are now covered,
   and which are intentionally deferred (with reasons).
